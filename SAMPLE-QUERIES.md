## Purpose
The following sample queries demonstrate how each database platform supports its designated workload within the proposed polyglot persistence architecture.
Rather than simply retrieving data, each query has been designed to align with the strengths of its underlying database engine, ensuring predictable performance, efficient resource utilization, and long-term scalability.
---

# SQL Server : Transactional Workloads
SQL Server acts as the authoritative system of record and is responsible for highly consistent transactional operations.
---

## Retrieve Active Device Information

```sql
SELECT
    d.device_identifier,
    d.device_code,
    d.device_name,
    d.sensor_type,
    d.device_status,
    d.location_name,
    d.registered_on
FROM asset.devices d
WHERE d.device_code = @device_code
  AND d.record_status = 'Active';
```

### Business Purpose
Retrieves the current device record used during device registration, monitoring, and API requests.

### Performance Characteristics
- Uses the unique index on **device_code**.
- Filtered index on **record_status** minimizes unnecessary page reads.
- Expected execution plan: **Index Seek**.
- Complexity: **O(log n)**.

---

## Retrieve Active Device Configuration

```sql
SELECT
    c.configuration_identifier,
    c.device_identifier,
    c.reporting_interval,
    c.threshold_value,
    c.effective_from
FROM configuration.device_configurations c
WHERE c.device_identifier = @device_identifier
  AND c.configuration_status = 'Enabled'
  AND c.effective_to IS NULL;
```

### Business Purpose
Retrieves the currently active configuration used to validate incoming sensor readings.

### Performance Characteristics
- Uses filtered composite index.
- Returns only active configurations.
- Minimal logical reads.
- Expected execution plan: **Index Seek**.
---

## Retrieve Critical Active Alerts

```sql
SELECT
    a.alert_identifier,
    a.device_identifier,
    a.alert_type,
    a.alert_severity,
    a.alert_status,
    a.triggered_on
FROM alert.alerts a
WHERE a.alert_status IN ('Open', 'Acknowledged')
  AND a.alert_severity = 'Critical'
ORDER BY a.triggered_on DESC;
```

### Business Purpose
Supports operational dashboards displaying active incidents requiring attention.

### Performance Characteristics
- Covered by filtered non-clustered index.
- Ordered retrieval avoids unnecessary sorting.
- Expected execution plan: **Index Seek + Ordered Scan**.
---

# TimescaleDB : Time-Series Analytics
TimescaleDB stores high-volume telemetry generated by connected devices.
Its architecture is optimized for sequential writes and time-based analytical queries.
---

## Retrieve Latest Sensor Readings

```sql
SELECT
    recorded_on,
    device_identifier,
    sensor_type,
    measured_value,
    measurement_unit,
    quality_status
FROM telemetry.sensor_readings
WHERE device_identifier = :device_identifier
ORDER BY recorded_on DESC
LIMIT 100;
```

### Business Purpose
Displays the most recent telemetry for real-time monitoring dashboards.

### Performance Characteristics
- Composite index on `(device_identifier, recorded_on DESC)`.
- Chunk pruning limits scanned partitions.
- Reads only recent data.
- Expected execution plan: **Index Scan with Chunk Pruning**.
---

## Hourly Telemetry Analytics

```sql
SELECT
    bucket,
    device_identifier,
    sensor_type,
    avg_value,
    min_value,
    max_value,
    total_readings
FROM telemetry.hourly_sensor_stats
WHERE device_identifier = :device_identifier
AND bucket >= NOW() - INTERVAL '7 days'
ORDER BY bucket DESC;
```

### Business Purpose
Provides historical analytics without repeatedly scanning raw telemetry.

### Performance Characteristics
- Uses Continuous Aggregate View.
- Eliminates expensive aggregation on raw data.
- Benefits from hypertable partitioning.
- Expected execution plan: **Continuous Aggregate Scan**.
---

# MongoDB : Audit & Operational Logging
MongoDB stores append-only operational events generated by the application.
The document model provides flexibility for evolving event structures while maintaining high write throughput.
---

## Retrieve Events by Correlation Identifier

```javascript
db.application_logs.find(
    {
        correlationId: "c8f9a2b1-4e2d-4f1a-8c3b-1a2b3c4d5e6f"
    }
).sort(
    {
        eventTimestamp: -1
    }
);
```

### Business Purpose
Supports distributed request tracing across application services.

### Performance Characteristics
- Compound index on `(correlationId, eventTimestamp)`.
- Efficient document retrieval.
- Minimal collection scan.
- Expected execution plan: **Indexed Query**.
---

## Retrieve Device Audit History

```javascript
db.application_logs.find(
{
    "payload.deviceIdentifier":"d1e2f3a4-5b6c-7d8e-9f0a-1b2c3d4e5f6a"
}
)
.sort(
{
    eventTimestamp:-1
}
)
.limit(50);
```

### Business Purpose
Displays recent operational history for a specific device.

### Performance Characteristics
- Compound payload index.
- Descending timestamp ordering.
- Limited result set.
- Expected execution plan: **Indexed Query**.

# Performance Summary

|-------------|--------------------------|---------------------------------------------------|-------------------------|
| SQL Server  | Transactional Processing | Primary Keys, Covering Indexes, Filtered Indexes  | Index Seek              |
| TimescaleDB | Time-Series Telemetry    | Hypertables, Chunk Pruning, Continuous Aggregates | Chunk-Aware Index Scan  |
| MongoDB     | Audit Logging            | Compound Indexes, TTL Indexes, Document Storage   | Indexed Document Lookup |
---

# Architectural Observations
The sample queries demonstrate that each database platform is responsible for workloads aligned with its native strengths.
- SQL Server delivers strong transactional consistency through indexed relational queries.
- TimescaleDB efficiently manages high-volume telemetry using hypertables, partitioning, and continuous aggregates.
- MongoDB provides flexible, high-throughput storage for append-only audit events.

This workload specialization minimizes resource contention, improves scalability, and enables each database platform to evolve independently while maintaining a consistent application architecture.
---

# Conclusion
The proposed query strategy reflects the overall architectural principle of **using the right database for the right workload**.
By combining SQL Server for transactional processing, TimescaleDB for time-series analytics, and MongoDB for operational logging, the solution delivers improved performance, predictable scalability, and efficient resource utilization while preserving clear separation of concerns across the data platform.
